## ۲. روش تصمیم و محدودیت‌ها
1. تطبیق عنوان فقط با NFKC، ي/ی، ك/ک، ة/ۀ→ه و حذف فاصله/نیم‌فاصله/نشانه‌گذاری است؛ واژه‌های تخصص/مقطع یا محتوای پرانتز حذف نشده‌اند. alias معنایی، fuzzy match، انتخاب با ظرفیت/بیشترین تعداد رکورد، و overlap جرقه‌ها **اصلاً استفاده نشده‌اند**. تطبیق‌نیافتن عنوان به معنی نبود رشته در سنجش نیست؛ فقط این matching محافظه‌کارانه شاهد دقیق پیدا نکرده است.
2. حضور یک عنوان در یک دفترچه، به‌خصوص پذیرش «صرفاً سوابق»، به تنهایی گروه پایهٔ یکتا نمی‌سازد. فایل‌ها هزاران رشته‌محل مشترک دارند. همه گروه‌های با آزمون و حضور سوابق نگه داشته شده‌اند؛ گروه‌های نامطلوب برای رسیدن به پیشنهاد دلخواه حذف نشده‌اند.
3. اگر تطبیق با آزمون فقط در یک گروه باشد، همان مبنای پیشنهاد است. اگر با exam_group کاتالوگ تعارض دارد (ID 172)، پیشنهاد اصلاح **مشروط به رأی ناظر** است، نه اصلاح خودکار. اگر با آزمون چندگروهی باشد، exam_group صریح کاتالوگ در همان گروه‌ها برای انتخاب شاخه اصلی استفاده می‌شود؛ ورود از گروه‌های دیگر انکار نمی‌شود.
4. بدون گروه یکتای دفترچه، exam_group صریح کاتالوگ مبناست؛ در نبود آن، group=هنر یا علوم انسانی مستقیماً به قاعده ناظر وصل می‌شود. پل دستهٔ مهندسی→ریاضی و زبان‌وادبیات→انسانی **پیشنهاد دسته‌بندی کاتالوگی** است، نه معادل‌سازی اثبات‌شده با گروه رسمی آزمون. چنین پیشنهادهایی در موارد تغییر با برچسب مشروط مشخص شده‌اند. مثال استثنا: ID 77 با group=مهندسی اما exam_group=هنر، طبق فیلد اختصاصی هنر باقی می‌ماند؛ همه مهندسی‌ها کورکورانه ریاضی نشده‌اند.
5. `علوم پایه`، `کشاورزی` و `کاردانی` به خودی خود یک گروه یکتا تعیین نمی‌کنند. در نبود exam_group یا شاهد یکتای دفترچه، نتیجه نامعین است. برای «زبان و ادبیات کردی» (۲۱۴)، خارجی بودن ادعا نشده؛ پیشنهاد انسانی صرفاً از دستهٔ زبان/ادبیات کاتالوگ است و تأیید قاعده می‌خواهد.
6. اولویت فوق برای تهیه جدول پیشنهاد صریح شده، نه به عنوان قانون جدید قطعی سنجش. تمام تغییرهای پیشنهادی، حتی موارد روشن، باید ناظر را تأییدکننده داشته باشند. پیشنهادهای مشروط به ویژه نیازمند انتخاب سیاست «شاخه اصلی» از میان مسیرهای متعددند.
7. هیچ import/اجرای engine، خواندن عددی S/V برای محاسبه، میانگین‌گیری یا شبیه‌سازی branch انجام نشده است؛ اسکریپت فقط فیلدهای کاتالوگ و رکوردهای دفترچه را بررسی می‌کند. نتایج PHASE0b مربوط به manifest همان مرحله‌اند؛ با تغییر منبع عضویت، نتایج قبلی را نباید اثباتِ candidate جدید دانست.

### نکات تعارض که ناظر باید صریحاً انتخاب کند
- **۱۷۲، معماری داخلی:** C می‌گوید group=هنر، exam_group=هنر و high_school_branch=فنی و حرفه‌ای. دفترچه R دقیقاً ۴ رکورد با آزمون دارد؛ نمونه R[973]، کد 30518، ص۷۵، عنوان «معماري داخلي». در H/T/E/Z تطبیق‌ها صرفاً سوابق‌اند. پیشنهاد این سند «ریاضی فیزیک» با اولویت شاهد با آزمون است؛ اگر ناظر سیاست موضوعی هنرِ کاتالوگ را ترجیح دهد، رد این پیشنهاد و حفظ فنی باید صریح ثبت شود، نه اینکه تعارض پنهان شود.
- **۲۰۱–۲۰۴:** هر عنوان در R و T با آزمون وجود دارد؛ چهار مورد را «فقط ریاضی در سنجش» ننامیده‌ایم. پیشنهاد ریاضی از group=مهندسی برای انتخاب شاخه اصلی است، نه از overlap. ناظر باید این tie-break را بپذیرد یا شاخه را نامعین/متفاوت اعلام کند.
- **۲۰۸، علوم قضایی:** با آزمون در R/T/E حضور دارد؛ group=علوم انسانی کاتالوگ مبنای پیشنهاد انسانی است. exam_group آن null است، پس این مورد نیز تصمیم تأییدی می‌خواهد.
- **۲۱۴:** هم‌عنوان در پنج دفترچه اما فقط سوابق؛ دستهٔ زبان و ادبیات منبع پیشنهاد انسانی است. گروه آزمون زبان خارجی برای کردی از این داده‌ها اثبات نشده است.
- **۲۱۹–۲۲۰:** همه دفترچه‌ها رکورد سوابق هم‌عنوان دارند و group=کشاورزی است. از داده حاضر شاخه اصلی یکتا حاصل نمی‌شود؛ رأی ناظر/منبع تکمیلی لازم است. نگاشت کدی قبلی به ریاضی، منبع معتبر این مرحله نیست.

## ۶. حکم و حدود PR بعدی
**Go برای بررسی/رأی روی همین سند؛ No-Go برای write یا Merge metadata تا تأیید ناظر روی جدول.** در وضعیت حاضر PR فقط docs است. هیچ تغییر engine، میانگین school_branches یا Merge موتور پیشنهاد نمی‌شود.
- پس از تأیید، PR اجرایی **جدا** فقط برای فیلد `high_school_branch` از idهای دقیقِ مصوب در `majors_database_v2.json`؛ نه `exam_group/group`، نه کد/S/V/activation و نه school_branches. فهرست اختلاف تأییدشده باید قبل از write بسته شود. تمام مقادیر باید از چهار name دقیق موجود باشند.
- ۱۷۵ فعال سازگار نباید بازنویسی یا «تمیزسازی» شوند؛ ۲۸ غیرفعال خارج scope‌اند. ۲۱۹–۲۲۰ تا رأی یا منبع تکمیلی null بمانند؛ پیشنهادهای مشروط بدون رأی صریح به patch قطعی تبدیل نشوند. ناظر می‌تواند بخشی از ۲۵ پیشنهاد را تأیید کند؛ بقیه متوقف می‌مانند.
- HEAD تازه deploy قبل از PR بعدی دوباره pin شود. اگر منبع تغییر کرد، جدول باید بازپخش و delta توضیح داده شود. diff آینده باید ثابت کند جز high_school_branchهای مصوب هیچ فیلدی عوض نشده؛ موتور/میانگین/گیت در این مرحله اجرا نشود. این سند جایگزین تست‌های لازم و مجوز مستقلِ بازسازی آتی شاخه نیست.
- rollback احتمالی PR metadata آینده فقط مقدارهای قبلی همان field/idهاست؛ هیچ revert موتور، ۴۲ وزن DH-013، کل catalog یا branch JSON مجاز به استنباط از این سند نیست.
- نتیجه فعلی فقط ممیزی منبع و metadata است؛ CI/live/fingerprint یا بهبود توصیه‌گر ادعا نشده است.

## ۷. کنترل‌های فقط‌خواندنی و اثر انگشت منابع
