## ۲. روش و حدود احراز منشأ/مجوز

- checkout نشست ابتدا پاک بود. تاریخچهٔ کم‌عمق main برای دسترسی به والدهای واقعی با fetch/deepen تکمیل شد؛ سپس log فقط روی سه مسیر اختلاف خوانده شد. هیچ checkout شاخهٔ دیگر یا انتقال درخت داده انجام نشد.
- مقایسهٔ JSON بر کلید `code`، `id` و `name` و سپس فیلد انجام شد، نه شمار خطوط diff. روی commitهای دادهٔ deploy از ۲۰۲۶-۱۰-۱۹ به بعد، مقدار فیلد با والد اول مقایسه و آخرین تغییر معناییِ برابر با مقدار جاری پیدا شد. همهٔ فیلدهای متفاوتِ فعلی در این بازه منشأ قابل‌ردیابی داشتند.
- برای نمونه‌ها، blame تک‌خطی/محدود روی description، یک عدد واقعاً متفاوت از S و V، انتساب و metadata اجرا شد. نمونهٔ blame یک عدد، منشأ کل ماتریس را به‌تنهایی ثابت نمی‌کند؛ نتیجهٔ ماتریس از مقایسهٔ کامل فیلد در تاریخچه است.
- state/base/merge SHA واقعی PRهای مربوط و کامنت‌هایشان از GitHub خوانده شد. همهٔ Mergeهای ذکرشده جدِ deploy مقایسه‌شده‌اند.
- **R = گزارش صریح اجرای مجوز ناظر:** در بدنه یا کامنت پس از Merge نوشته شده «طبق دستور/با مجوز ناظر». شاهد، گزارش ثبت‌شده در GitHub است؛ متن اصلی همهٔ پیام‌های ناظر خارج از GitHub مستقلاً در دسترس نبود.
- **G = Merge قطعی، سند دستور صریح احراز نشده:** PR واقعاً MERGED و جد deploy است، اما در body/comments/reviews خوانده‌شده گزارش صریح صدور/اجرای دستور آن Merge یافت نشد. این **اثبات بی‌مجوزبودن نیست**؛ نیاز به بازیابی دستور دارد. blame منشأ داده را نشان می‌دهد، نه اختیار انسانیِ Merge را.
- وجود متن تاریخی «Draft/no merge» در ابتدای PR را با وضعیت نهایی اشتباه نگرفتیم؛ گزارش پس از Merge و API ملاک تفکیک زمانی‌اند. اعتبار تجربی یا منشأ علمی اولیهٔ عددگذاری از صرف Git blame اثبات نمی‌شود.
