# ظرفیت پایلوت و SLO — نسخهٔ پیشنهادی ۱

**وضعیت: فاز ۰ سند ظرفیت آمادهٔ بازبینی؛ فاز ۱ فقط اسکلت QA. بدون تست بار، تغییر runtime یا تأیید ظرفیت.**

دامنه: پایلوت محدود و دعوتی با پشتیبانی مشخص؛ **نه پوشش ملی**، نه پذیرش عمومی نامحدود. منبع فرانت main؛ منبع API/DB `deploy/liara-commercial-sandbox`. اعداد زیر فرض برنامه‌ریزی و قابل‌ویرایش ناظرند؛ تا آزمون بار و پایلوت واقعی، تعهد بازاریابی یا SLA قراردادی نیستند.

## A) ظرفیت فرضی قابل تصویب

| پارامتر | فرض اولیهٔ v1 | تعریف |
|---|---:|---|
| کاربر فعال روزانه | ۲۰۰۰ | هدف برنامه‌ریزی پایلوت از سناریوی جذب زیر؛ حساب یکتایی که سفر را آغاز یا ادامه می‌دهد، نه درخواست یا حساب ثبت‌شده |
| کاربر هم‌زمان فعال در پیک | ۱۰۰ | کاربر در پنجرهٔ ۵ دقیقه‌ای تعامل؛ معادل ۱۰۰ درخواست in-flight نیست |
| تکمیل سفر در ساعت اوج | ۲۰۰ | دریافت نتیجهٔ اصلی؛ AI معیار تکمیل نیست؛ نرخ میانگین حدود ۰٫۰۵۶ تکمیل/ثانیه و نه RPS کل API |
| طول پایلوت پیشنهادی | ۷ روز فعال پس از پذیرش فنی | سقف دعوت‌ها و برنامهٔ جذب توسط ناظر کنترل شود |
| محدودیت دامنه | دعوتی، شروع مرحله‌ای | در صورت عبور از ظرفیت آزموده‌شده دعوت جدید متوقف شود؛ سفرهای باز بی‌دلیل بسته نشوند |

### مبنای عدد روزانه — سناریو، نه پیش‌بینی تقاضا

جمعیت سالانهٔ **حدود ۲ میلیون دانش‌آموز، فرض ارائه‌شدهٔ ناظر** است؛ در این سند آمار مستقل جمعیت تأیید نشده است. میانگین سادهٔ پوشش کامل طی ۳۶۵ روز حدود ۵۴۸۰ کاربر جدید/روز است، اما برای برنامه‌ریزی فصلی کافی نیست.

- فرض جذب اولیهٔ قابل‌ویرایش: **۵٪** جامعهٔ سالانه = ۱۰۰ هزار کاربر یکتا، طی **۶۰ روز** = حدود **۱۶۷۰ کاربر جدید/روز**. این سهم جذب و بازه، فرض برنامه‌ریزی‌اند، نه شاهد بازار.
- با فرض بازدید مجدد حدود ۲۰٪ معادل ورودی روزانه، هدف گرد‌شدهٔ **۲۰۰۰ کاربر فعال روزانه** برای پایلوت انتخاب شد. نرخ بازگشت، هم‌پوشانی حساب‌ها و نوسان روزانه باید با دادهٔ پایلوت اصلاح شوند؛ این حاشیه تضمین پوشش پیک نیست.
- پایلوت ۷روزه، بخش کنترل‌شدهٔ همین مدل جذب است؛ نه تعهد به جذب ۱۰۰ هزار نفر در هفت روز. تعداد دعوت باید به ظرفیت آزموده‌شده محدود بماند.
- برای مقایسه، پوشش **تمام ۲ میلیون نفر در ۶۰ روز** حدود **۳۳۳۰۰ کاربر جدید/روز** می‌خواهد؛ در سناریوی تنش با ضریب فرضی ۳ برای روز پیک، حدود **۱۰۰ هزار کاربر جدید/روز**، پیش از افزودن کاربران بازگشتی. این اعداد هدف آیندهٔ جداگانه‌اند و ظرفیت فعلی یا پایلوت را توصیف نمی‌کنند.

تغییر روزانه به ۲۰۰۰، اثبات کفایت ۱۰۰ کاربر هم‌زمان یا ۲۰۰ تکمیل در ساعت اوج نیست. این دو عدد فعلاً baseline پایلوت‌اند و پیش از تست بار باید با مدت نشست، زمان فعالیت روزانه و توزیع تکمیل تطبیق داده شوند؛ افزایش روزانه را نباید خودکار به RPS تبدیل کرد. RPS باید از تعداد درخواست هر سفر، زمان فکرکردن و burst ورود محاسبه و سپس اندازه‌گیری شود؛ ثبت‌نام، login، موتور و AI بار یکسانی ندارند. مدل کاربر تست نباید پاسخ‌ها را با سرعت غیرانسانی تمام کند و بعد به‌عنوان بار انسانی معرفی شود.

## SLO پیشنهادی، نه نتیجهٔ اندازه‌گیری

| مسیر | هدف p95 | نرخ خطای هدف |
|---|---:|---:|
| login معتبر | ≤۲ ثانیه | ≤۱٪ خطای غیرمنتظره |
| quota / ذخیرهٔ عملیاتی / مصرف یک‌بارهٔ سفر | ≤۱ ثانیه برای هر درخواست | ≤۱٪ خطای غیرمنتظره؛ **صفر نقض صحت اعتبار/مالکیت** |
| محاسبه و تحویل نتیجهٔ اصلی | ≤۳ ثانیه | ≤۱٪ خطای غیرمنتظره |
| بارگذاری خانه در مرورگر آزمایشی | ≤۵ ثانیه تا آماده‌شدن شروع | گزارش جدا از API، با مشخصات دستگاه/شبکه و cache سرد/گرم |

- latency در سمت client تست، شامل شبکهٔ همان محیط تا دریافت پاسخ کامل اندازه‌گیری شود؛ queue time حذف نشود. مرورگر واقعی برای معیار خانه لازم است؛ HTTP-only معادل UX نیست.
- برای هر مسیر: تعداد، p50/p95/p99، timeout، نرخ خطا و مشخصات محیط جدا ثبت شوند. خطا/timeout نباید از گزارش latency و نرخ شکست ناپدید شوند؛ timeoutها جدا شمارش و اثرشان صریح ثبت شود.
- نرخ خطای غیرمنتظره = 5xx، خطای شبکه، timeout و پاسخ غیرمنتظرهٔ سناریوی معتبر تقسیم بر همهٔ تلاش‌های معتبر همان مسیر. خطاهای مورد انتظار تست منفی جدا هستند. 429 در بار عادی مجاز، failure هدف کاربر و مصرف بودجهٔ خطاست؛ در سناریوی abuse انتظار کنترل است و جدا گزارش می‌شود.
- قضاوت فنی اولیه روی بخش steady حداقل ۶۰ دقیقه، با شمار نمونهٔ کافی و توزیع بار ثبت‌شده برای هر مسیر است. اگر نمونه برای p95 کم بود، نتیجه «شاهد ناکافی» است نه PASS. مجموع روزانه نباید failure پنجرهٔ پیک را بپوشاند.
- معیار عددی با تست شبکه/موقعیت مشخص معتبر است؛ آن را وعدهٔ یکسان برای همهٔ اینترنت‌ها و دستگاه‌های ایران نکنیم. این SLO هنوز availability ماهانه یا ظرفیت ملی تعریف نمی‌کند.

## AI خارج از مسیر حیاتی

**قرارداد هدف:** قطع، timeout یا اشباع AI نباید مانع نمایش/ذخیرهٔ نتیجهٔ اصلی، ادامهٔ سفر یا بازیابی آن شود. درخواست مشاوره مجزا با وضعیت روشن و رفتار خطای کنترل‌شده باشد؛ هزینه و هم‌زمانی آن جدا اندازه‌گیری شود. موفقیت نتیجهٔ اصلی، موفقیت AI را ثابت نمی‌کند و برعکس.

این دور queue، Redis یا تغییر API پیاده نمی‌کند و جداسازی کامل منابع فعلی را تأیید نمی‌کند. در تست آینده، AI با mock/fault injection کنترل شود؛ هزینهٔ واقعی ارائه‌دهنده یا ارسال دادهٔ دانش‌آموز مجاز نیست مگر تأیید جدا. اگر اختلال AI روی نتیجه اثر گذاشت، این معیار FAIL است و طراحی مستقل لازم می‌شود.

## B) اسکلت فاز ۱ — چک‌لیست صحت هم‌زمانی

**وضعیت تمام ردیف‌ها: NOT RUN در این موج.** وجود تست قبلی معادل اجرای این سناریوها در این موج نیست. PostgreSQL ایزوله، migration صحیح، کاربر و دادهٔ مصنوعیِ محلی و gateway جعلی پیش‌نیازند. روی production تست بار، ثبت‌نام جعلی یا callback ساختگی اجرا نشود.

| شناسه | سناریو و تحریک | invariant پذیرش | شاهد لازم |
|---|---|---|---|
| C01 | ۱۰ double-submit هم‌زمان برای consume یک journey از یک کاربر؛ سپس retry بعد از timeout شبیه‌سازی‌شده | فقط یک مصرف مؤثر؛ اعتبار غیرمنفی؛ ledger یکتا و مالکیت ثابت؛ پاسخ‌های retry مطابق قرارداد API، نه الزاماً همگی 200 | اعتبار قبل/بعد، شمار ledger و statusها؛ بدون token/شناسهٔ واقعی |
| C02 | دو journey متفاوت با یک اعتبار باقی‌مانده، شروع هم‌زمان | حداکثر یک سفر شارژ شود؛ دیگری خطای کنترل‌شده؛ هیچ منفی‌شدن یا double-spend | transaction/ledger و پاسخ هر دو؛ DB واقعی برای قفل/constraint |
| C03 | callback تکراری یک payment، بار اول موازی و سپس retry؛ event key یکسان و متفاوت؛ حالت verification ناموفق | یک payment موفق حداکثر یک grant مطابق قرارداد؛ ناموفق صفر grant؛ مبلغ/کاربر از مرجع سرور، نه payload قابل‌اعتماد مشتری | gateway mock و شمار entitlement/event؛ **بدون پرداخت یا درگاه واقعی** |
| C04 | ذخیرهٔ موازی یک session/result با payload یکسان و متفاوت | مالکیت و ساختار معتبر؛ عدم رکورد تکراری/نیمه‌کاره و ارتباط غلط؛ سیاست تعارض پیش از تست مشخص شود | مقدار پایدار DB و پاسخ تعارض/retry؛ سیاست «آخرین نویسنده» از پیش فرض نشود |
| C05 | دو کاربر مصنوعی A/B؛ B شناسهٔ session/result متعلق به A را در read/save/consume/counsel امتحان کند | عدم افشا، عدم overwrite یا مصرف اعتبار A؛ deny مطابق قرارداد بدون نشت payload | statusها و countهای DB؛ نقش admin با کاربر عادی اشتباه نشود |
| C06 | سفر نیمه‌کاره روی release N؛ فرانت N+1، reload/resume، یک تب قدیمی و یک تب تازه | پاسخ‌ها و canonical S index/V code، ترتیب نمایشی همان سفر، sessionId و شارژ معتبر حفظ شوند؛ بدون مصرف مجدد | مرورگر/VM و state مصنوعی قبل/بعد؛ SW/cache جدا بررسی شود |
| C07 | خطا/timeout AI هنگام محاسبه و ذخیرهٔ اصلی؛ سپس retry مشاوره | نتیجهٔ اصلی و سفر قابل دسترسی بماند؛ خطای روشن و کنترل‌شده؛ تکرار مشاوره شارژ سفر را تکرار نکند | mock ارائه‌دهنده و timeline مسیرهای مستقل؛ بدون ارسال دادهٔ واقعی |

**مسئلهٔ باز قبل از C04:** قرارداد version/conflict ذخیره از source تجاری استخراج شود. اگر حل تعارض تعریف نشده بود، یافته ثبت و تصمیم طراحی خواسته شود؛ این سند آن را به‌صورت حدسی پیاده نمی‌کند.

### اجرای پیشنهادی پس از تأیید ناظر

- [ ] SHA فرانت و backend، hash فایل runtime (نه فقط GIT_COMMIT env)، release ID و migrations ثبت شوند.
- [ ] مشخصات CPU/RAM، worker/replica، DB pool، proxy و latency شبکه ثبت شود؛ secret/env dump ثبت نشود.
- [ ] C01 تا C07 ابتدا با PostgreSQL ایزوله اجرا شوند؛ DB ناموجود = BLOCKED، نه PASS و نه اثبات باگ تولید.
- [ ] سپس با مجوز جدا، بار ۱۰ → ۲۵ → ۵۰ → ۱۰۰ کاربر فعال مدل‌شده با think time و توزیع مسیر واقعی؛ steady و burst جدا. هنوز script بار یا dispatch ایجاد نشده است.
- [ ] پیش از افزایش بار: صفر نقض صحت، پاسخ‌های قابل انتظار، مشاهدهٔ مصرف منابع و اتصال DB. هر نشت داده/double-charge: توقف فوری. خطای بالاتر از ۱٪ یا p95 بالاتر از هدف در دو پنجرهٔ ۵ دقیقه‌ای: توقف افزایش بار و بررسی شاهد، نه خرید فوری infra.
- [ ] یک افت و بازیابی کنترل‌شده/قطع ارتباط در محیط ایزوله برای بررسی retry؛ rollback و backup/restore با مجوز مستقل.
- [ ] نتایج با PASS/FAIL/BLOCKED/NOT RUN، تعداد نمونه، مدت، SHA و علت ثبت شوند؛ اگر صحت FAIL باشد، latency سبز اجازهٔ عبور نمی‌دهد.

## حفاظت شواهد و خروجی فاز

لاگ مجاز: شناسهٔ تصادفی اجرای تست، نام مسیر بدون query حساس، status، duration، شمار رکورد/اعتبار و نتیجهٔ assertion. password، token، Authorization، cookie، شماره، پاسخ/نتیجهٔ فردی، prompt AI، اطلاعات پرداخت و dump DB در log/کامنت/آرتیفکت ممنوع‌اند. correlation ID تست باید مستقل از شناسهٔ واقعی کاربر باشد. fixture مصنوعی نباید با حساب حقیقی در Liara ساخته شود.

خروجی این دور: همین سند و Draft فقط‌مستندات. فاز ۰ به معنی تکمیل پیشنهاد و آماده‌بودن برای تصویب ناظر است؛ اعداد هنوز مصوب یا اندازه‌گیری‌شده نیستند. فاز ۱ صرفاً اسکلت است و اجرای آن ادعا نشده است. هیچ تغییر موتور، وزن، majors، micro_motives، Hybrid، Cutover، Total، خرید/سهمیه یا CI؛ هیچ خرید زیرساخت یا الزام Redis؛ هیچ Deploy، تست بار production یا Merge بدون دستور ناظر.
