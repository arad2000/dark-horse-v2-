## ۲. نقش شاخه‌ها

### deploy: منبع ساخت backend عملیاتی

- ساخت backend باید از commit مشخص و بازبینی‌شدهٔ `deploy/liara-commercial-sandbox` انجام شود؛ artifact باید SHA و hash manifest داشته باشد.
- وجود کد در deploy به‌تنهایی مجوز استقرار، migration یا استفاده از credential عملیاتی نیست.
- Merge PR و استقرار دو مجوز مستقل‌اند؛ هر دو تابع سیاست و تأیید ناظر هستند.
- پوشش داده یا سبزشدن چند تست جایگزین سلامت runtime، readiness یا گیت‌های اجباری نیست.

### main: فرانت‌اند منتشرشونده و مسیر پذیرش کنترل‌شدهٔ مرجع

- طبق workflow فعلی، فرانت‌اند Pages از `main/docs` منتشر می‌شود. Merge به main می‌تواند workflow انتشار Pages را خودکار فعال کند؛ مجوز Merge #310 فقط برای اسناد صادر شده است، نه استقرار backend یا migration.
- **main تا پذیرش PRهای محدودِ رفع اختلاف، منبع اجباری بایت‌به‌بایت سه JSON علمیِ runtime نیست.** منشأ runtime داده و کد، deploy مصوب است؛ اختلاف‌ها در بخش ۴ ثبت شده‌اند و باید محدود و مستند تعیین تکلیف شوند.
- checkout فعلی main مبنای قابل‌اتکای اجرای backend کامل نیست: چند ماژول importشده و `trait_map_v3.json` ریشه در tree آن وجود ندارند. این یک محدودیت موجود است، نه تأیید آن به‌عنوان طراحی مطلوب.
- تا اصلاح مستقل packaging و راهنمای اجرا، README نباید به‌عنوان شاهد قابلیت اجرای backend از main تلقی شود. این PR README یا کد را تغییر نمی‌دهد.
- برای رفع این محدودیت، انتقال عمومی همهٔ تغییرات deploy به main یا ادعای اینکه main عمداً برای همیشه frontend-only است مجاز نیست؛ دامنهٔ backend در main تصمیم و PR مستقل می‌خواهد.

## ۳. قرارداد سه فایل مرجع

برای هر سه فایل، **منبع runtime نسخهٔ مصوب deploy است؛ main تا PRهای محدودِ تعیین تکلیف اختلاف‌ها، منبع اجباری بایت‌به‌بایت آن‌ها نیست.** این دورهٔ گذار نه مجوز تغییر خودسرانهٔ داده است و نه استثنای دائمی برای گیت.

## ۵. تصمیم قفل‌شده دربارهٔ گیت canonical در دورهٔ گذار

**گیت اجرایی فعلی در #310 حفظ می‌شود؛ main فعلاً الزام بایت‌به‌بایت سه JSON runtime نیست. ناسازگاری سیاست اجرایی گیت با این قرارداد، بدهی صریح برای PR محدود بعدی است، نه مجوز دورزدن یا سبز اعلام‌کردن آن.**

- `reference_data_sync_audit.py` و workflowهای مصرف‌کننده در این PR بدون تغییر می‌مانند.
- کد فعلی هنوز برابری دقیق شش فایل را می‌سنجد؛ در این PR حذف، skip، ضعیف یا با allowlist کلی جایگزین نمی‌شود. این توصیف رفتار موجود است، نه الزام قراردادی برای بازگرداندن دادهٔ runtime به main قدیمی.
- همگام‌کردن کور main با deploy ممنوع است. برای هر اختلاف، منشأ، معنای علمی، وابستگی‌ها و diff دقیق باید ابتدا تأیید شود؛ ممکن است بخشی از اختلاف به اصلاح deploy نیاز داشته باشد، نه انتقال به main.
- پذیرش school به‌تنهایی اختلاف majors و micro را رفع نمی‌کند؛ تا تعیین تکلیف تمام اختلاف‌های مشمول گیت، ادعای عبور canonical، آمادگی cutover یا Merge‌پذیری نسخهٔ اجرایی مجاز نیست.
- شکست‌های fingerprint تاریخی مسئلهٔ جداگانه‌اند: expected fingerprint برای سبزشدن عوض نمی‌شود. اگر normalization محدودِ metadata مصوب لازم باشد، باید اعتبارسنجی مقدار جاری و کنترل‌های منفی داشته باشد و جداگانه تصویب شود.
- هر تغییر بعدی گیت برای تطبیق با قرارداد جدید، به طرح کنترل جایگزین، اعتبارسنجی provenance و بازبینی مستقل نیاز دارد؛ این سند مجوز پیاده‌سازی یا تضعیف گیت نیست.

## ۶. معیار قفل‌شدن قرارداد

۱. ناظر نقش runtime=deploy و عدم الزام بایت‌به‌بایت main برای سه JSON تا PR محدود را صریحاً تأیید کرده است.
۲. ناظر مسیر رفع سه اختلاف را در PRهای مستقل بپذیرد؛ خودِ رفع اختلاف شرط لازم برای «سبز» اعلام‌کردن گیت است، نه الزام اینکه داخل PR اسناد انجام شود.
۳. diff این PR فقط همین قرارداد و سند ممیزی باشد؛ هیچ فایل runtime یا داده‌ای تغییر نکند.
۴. ناظر صریحاً خروج #310 از Draft و Merge آن را مجاز کرده است؛ قفل قرارداد با Merge همان diff اسنادی تکمیل می‌شود. این مجوز به PR اجرایی بعدی تعمیم نمی‌یابد.

## ۷. گام بعد، فقط پس از قفل قرارداد

PR مستقل برای **fail-closed شدن لود reference موتور**:

- قبل از ready شدن، وجود فایل‌ها، JSON معتبر، schema، یکتایی شناسه‌ها/کدها و قرارداد ابعاد/دامنه بررسی شود.
- در دادهٔ ضروری ناقص، موتور ظاهراً آماده با map خالی نسازیم؛ readiness باید ناموفق و خطای روشن باشد.
- ابتدا قرارداد رفتار خطا و تست‌های خرابی فایل/ورودی تهیه شود؛ هیچ وزن، فرمول، threshold، activation یا متن علمی تغییر نکند.
- startup، readiness و liveness از هم تفکیک شوند؛ این تغییر به معنی مجوز اتصال DB، migration، AI یا سرویس زنده نیست.
- در این PR اسنادی هیچ‌یک از این اصلاحات شروع نمی‌شود.
