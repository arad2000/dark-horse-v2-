# DH-013 — پروتکل نگاشت Micro Motive به فردیت رشته

**شناسه:** DH-013  
**نسخه:** reviewer-approved operational v1  
**کاربرد:** فاز ۲ فردیت رشته‌های جدید اسب سیاه  
**ترتیب اجباری:** تعلق محله ← Motive ← امضای فردیت ← تمایز همسایه ← وزن ← آزمون ← JSON نهایی

## ۱. اصل حاکم

تنها شاهد مجاز برای ساخت مدل فردیت یک رشته، Micro Motiveهای مشخص و قابل ردیابی است. وزن نباید ابتدا ساخته و سپس با کدهای Motive تزئین یا توجیه شود. این پروتکل مجوز تغییر موتور، Hybrid، cutoff یا فرمول Total نیست.

## ۲. مراحل دوازده‌گانه

### مرحلهٔ ۱ — قفل تعلق و قرارداد کد
- محله و زیرمحله باید ابتدا در فاز ۰ تعیین شوند.
- پیشوند هر micro_motive_code باید در majorCodes همان زیرمحله مجاز باشد.
- اگر پیشوند/زیرمحله هنوز وجود ندارد، ابتدا قرارداد داده‌ای جداگانه و با تأیید ناظر اضافه شود؛ پیش از آن Motive ساخته نشود.
- اگر تعلق واقعاً مبهم است، نیازمند ناظر باقی بماند و رشته وارد موج Motive نشود.

### مرحلهٔ ۲ — بستن مجموعهٔ شواهد
- فقط بانک micro_motives.json و نسخهٔ متناظر UI که واقعاً برای محصول مصرف می‌شود، منبع شاهد هستند.
- برای هر شاهد، کد دقیق، شرح فارسی و دلیل ارتباط آن با رشته ثبت شود.
- نبود شاهد کافی با حدس، عنوان رشته، cluster تنها یا وزن رشتهٔ همسایه جبران نمی‌شود.

### مرحلهٔ ۳ — استخراج Core Enjoyment
- یک امضای لذت محوری از کاری توصیف شود که خودِ انجام آن برای فرد رضایت‌زاست.
- این امضا باید دست‌کم با ۳ Micro Motive پشتیبانی شود.
- فهرست مسئولیت‌ها، منزلت اجتماعی، درآمد یا «کمک به مردم» به‌تنهایی امضای لذت محسوب نمی‌شود.

### مرحلهٔ ۴ — استخراج Identity
- هویت کاری به شکل «فرد در حال انجام چه کنش مشخصی است» نوشته شود، نه با برچسب‌های کلی شخصیتی.
- هر بخش معنادار باید دست‌کم با ۲ Micro Motive پشتیبانی شود.
- شاهد مخالف یا Motiveهایی که فقط موضوعی‌اند اما کنش را پشتیبانی نمی‌کنند، جدا ثبت شوند.

### مرحلهٔ ۵ — تعیین Archetype
- archetype باید جمع‌بندی فشردهٔ کنش، هدف و سبک مسئله‌گشایی مستندشده در Motiveها باشد.
- آرکتایپ، تیپ شخصیتی فرد، عنوان جذاب تبلیغاتی یا بازنویسی نام رشته نیست.
- هر ادعای اصلی باید به شواهد مراحل ۲ تا ۴ قابل ردیابی باشد.

### مرحلهٔ ۶ — تعریف Fulfillment عینی
- fulfillment_source یک رویداد کاری/شناختی مشخص است که در آن نتیجهٔ رضایت‌بخش قابل مشاهده یا ارزیابی می‌شود.
- رویداد باید کنش، مسئله یا خروجی معین داشته باشد؛ از شعار و عبارت‌های غیرقابل آزمون پرهیز شود.

### مرحلهٔ ۷ — انتخاب رشته‌های همسایه
- نزدیک‌ترین رشته‌های مفهومی بررسی شوند؛ انتخاب صرفاً بر اساس cluster یا نام کافی نیست.
- برای هر همسایه، هم‌پوشانی در کار، ابزار یا خروجی و نیز تفاوت واقعی مستند شود.
- رشته‌ای با هم‌پوشانی زیاد نباید بی‌دلیل به‌عنوان مرجع برگزیده شود.

### مرحلهٔ ۸ — قفل تمایز و مرز تصمیم
- مشخص شود این رشته برای کدام نوع کنش/مسئله «بله» و برای کدام کنش مشابه «نه» است.
- پیشوندهای مشترک یا خانواده‌های دوپهلو باید با شرح محتوا از هم جدا شوند؛ پیشوند مشترک به معنی یکسان‌بودن Motive یا وزن نیست.
- اگر تمایز اثبات‌پذیر نیست، به مرحلهٔ وزن نروید و موضوع را برای ناظر ثبت کنید.

### مرحلهٔ ۹ — استخراج strategy_weights
- وزن‌های راهبردی فقط پس از تکمیل و تأیید شواهد Motive، Core Enjoyment، Identity، Archetype، Fulfillment و contrast استخراج می‌شوند.
- Strategy یعنی میزان همخوانی رشته با راهبردهای مدل؛ Strategy برچسب شخصیت دانش‌آموز یا رشته نیست.
- از آرایهٔ رشتهٔ مرجع کپی نکنید. هر مقدار باید بر اساس شواهد همین رشته و قرارداد رسمی مدل توجیه شود.
- schema باید با ساختار جاری پروژه سازگار باشد. در کاتالوگ کنونی نمونه‌های وزن‌دار، strategy_weights با ساختار ۲۵ ردیف × ۵ مقدار دیده می‌شود؛ این مشاهده مجوز حدس‌زدن معنای خانه‌ها یا تغییر schema نیست.

### مرحلهٔ ۱۰ — استخراج value_weights
- value_weights فقط پس از شواهد مراحل قبل تولید می‌شود و باید به ارزش‌های رسمی/سؤال‌های مدل و Motiveهای همین رشته قابل ردیابی باشد.
- در نمونه‌های مرجع فعلی ۳۰ کلید از Q1A تا Q15B دیده می‌شود؛ schema معتبر باید از رکورد و قرارداد نسخهٔ جاری خوانده شود.
- از مقدار رشتهٔ نزدیک، وزن cluster یا قضاوت شهودی به‌عنوان میان‌بُر استفاده نکنید.

### مرحلهٔ ۱۱ — آزمون جداسازی و اعتبارسنجی

پیش از پذیرش، این چک‌ها باید موفق باشند:

1. **کفایت شواهد:** حداقل ۲ Motive برای هر بخش معنادار و حداقل ۳ برای Core Enjoyment.
2. **سازگاری:** هر کد در بانک موجود است و پیشوند با majorCodes زیرمحلهٔ قفل‌شده مطابقت دارد.
3. **تمایز:** رشته در برابر همسایه‌های نزدیک تفاوت قابل شرح دارد و آزمون جداسازی نتیجهٔ معنی‌دار می‌دهد.
4. **ساختار:** کلیدها، ابعاد آرایه‌ها، دامنهٔ مقادیر و فرمت JSON با schema معتبر پروژه می‌خواند.
5. **ردیابی شواهد:** برای هر تصمیم مهم، مسیر از Motive به استنباط و سپس وزن ثبت شده است.
6. **محافظت رگرسیون:** رشته‌های قدیمی، وزن‌های موجود، مسیر engine، Hybrid، cutoff و فرمول Total تغییر ناخواسته نکرده‌اند.
7. **بازگشت به مرحلهٔ مربوط:** نقص شواهد، شکست جداسازی یا ناسازگاری زیرمحله با دستکاری پنهانی آستانه/وزن پوشانده نمی‌شود.

### مرحلهٔ ۱۲ — JSON نهایی و فعال‌سازی
- تنها پس از عبور از همهٔ آزمون‌ها و تأیید ناظر، Motiveها، strategy_weights، value_weights، archetype، fulfillment_source، subgroup و weights_version در JSON نهایی ثبت شوند.
- motive_driven=true فقط برای رکورد کامل و تأییدشده فعال شود؛ رکورد ناقص باید catalog-only بماند.
- هر موج یک محله را پوشش دهد و PR آن محدودهٔ رشته‌ها، شواهد، تست‌ها و diff مشخص داشته باشد.

## ۳. قرارداد حداقلی شواهد

برای هر رشته، بستهٔ evidence باید شامل این موارد باشد:

- major_id و major_name، محله، زیرمحله و نسخهٔ قرارداد پیشوند
- micro_motive_codes و شرح هر کد
- نگاشت هر Core Enjoyment، Identity، Archetype و Fulfillment به کدهای پشتیبان
- جدول Neighbor contrast و دلیل تمایز
- rationale ثبت‌شده برای strategy_weights و value_weights
- خروجی آزمون جداسازی، اعتبارسنجی schema و regression
- تأیید ناظر و نسخهٔ پروتکل

## ۴. ممنوعیت‌ها

- وزن‌سازی قبل از Motive و افزودن Motive پس از آن برای توجیه وزن
- ساخت انبوه بر اساس cluster، نام رشته یا رشتهٔ مرجع بدون evidence
- کپی کور strategy_weights یا value_weights
- تولید Motive از prefixی که هنوز در majorCodes زیرمحله مجاز نشده است
- تغییر موتور، Hybrid، cutoff، فرمول Total یا رکوردهای قدیمی خارج از مجوز مشخص
- Merge بدون تأیید ناظر؛ این پروتکل به‌تنهایی مجوز Merge نیست

## ۵. ارتباط با فاز ۰

سند DH-PHASE0-AFFILIATION-v1 مرجع تعلق پیش از وزن است. جدول همان سند، موارد نیازمند تصمیم ناظر را از قراردادهای prefix/subrealm جدا می‌کند. اختلاف در تعلق باید قبل از ورود به مراحل ۲ تا ۱۲ حل شود.

**قاعدهٔ نهایی:** تعلق → Motive → Core Enjoyment / Identity / Archetype / Fulfillment → Neighbor contrast → مشتق Strategy / Value weights → آزمون جداسازی → JSON نهایی و فعال‌سازی.
