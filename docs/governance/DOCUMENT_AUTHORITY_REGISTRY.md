## 1. هدف و اصل حاکم

این رجیستری مرجعیت، تقدم، دامنه و وضعیت تصویب اسناد علمی و ابزارهای اعتبارسنجی را تعیین می‌کند تا هیچ فایل داده، برچسب نسخه، PR یا اجرای CI به‌تنهایی جایگزین تصمیم علمی و provenance نشود.

زنجیرهٔ کنترل:

`مرجع روش‌شناختی → استاندارد متن → شواهد رشته → وزن S/V → عضویت/شاخه → fingerprint → validator → موتور و runtime`

**اصل‌ها:**
- main و deploy نقش‌های متفاوت دارند؛ main مرجع علمی خودکار برای داده‌های runtime شاخهٔ deploy نیست.
- تفاوت blob میان main و deploy به‌تنهایی خطا یا مجوز sync نیست.
- PASS ساختاری، PASS fingerprint یا برچسبی مانند FINAL، به‌تنهایی تأیید علمی نیست.
- هر تصمیم باید به سند/commit، داده/ blob، شواهد، بازبین و دامنهٔ دقیق متصل باشد.
- تغییرات وزن، عضویت، متن evidence، محتوای تفسیری و اجرای فنی باید جداگانه دیده شوند؛ موفقیت یک لایه شکست لایهٔ دیگر را نمی‌پوشاند.

### 2.1 قاعدهٔ حل تعارض

اگر دو سند دربارهٔ یک قاعده تعارض یا ابهام داشته باشند:
1. دامنه و بند دقیق هر دو سند ثبت می‌شود.
2. سند پایین‌دست مجاز نیست حکم بالادست را بی‌صدا تغییر دهد.
3. برای تفسیر یا اصلاح متن بالادست، decision record صریح ناظر و PR مستنداتی لازم است.
4. تا رفع تعارض، فقط مرحله‌ای متوقف می‌شود که اجرای آن به بند مبهم وابسته است؛ دادهٔ موجود خودکار بازنویسی نمی‌شود.

### 2.2 قاعدهٔ confidence کمتر از 0.7

طبق تصمیم صریح ناظر:
- وقتی confidence کمتر از 0.7 است، میانگین وزنی رشته‌های همسایه **مکمل و تعدیل‌کننده** است؛ جایگزین شواهد خود رشته نیست.
- هفت متن micro-motive همان رشته و نگاشت دقیق آن‌ها به سؤال/گزینه‌ها، مبنای اصلی باقی می‌ماند.
- همسایه باید بر اساس معیارهای هویتی/تجربهٔ کاری و neighbor contrast مستند انتخاب شود؛ صرف تعلق به یک cluster یا شباهت عنوان کافی نیست.
- پرونده باید شناسه و دلیل انتخاب همسایه‌ها، وزن هر همسایه، confidence اولیه، وزن محلی، میانگین مکمل، مقدار نهایی و استدلال هر تعدیل را نگهداری کند.
- DH-013 فعلی ضریب عددی مشخصی برای ترکیب مقدار محلی و میانگین همسایه نمی‌دهد. ضریب دلخواه ساخته نمی‌شود؛ فرمول بازتولیدپذیر باید در نسخهٔ اصلاح‌شدهٔ پروتکل ثبت و جداگانه تصویب شود.
- confidence زیر 0.7 به‌تنهایی به‌معنای freeze خودکار نیست؛ اگر شواهد محلی و همسایگی ناسازگار باشند، اختلاف باید برای بازبینی مستقل ثبت شود.

## 3. استاندارد پذیرش micro-motive

#285 در جایگاه مکمل محتوایی DH-013 پذیرفته شده است، ولی متن فعلی تا دو review واقعی و مستقل تکمیل و تثبیت نشود، نسخهٔ نهایی مصوب نیست.

شرایط محتوایی:
- حوزه باید از خود جمله قابل تشخیص باشد؛ درج نام رشته یا عبارت کلی «در این رشته» کافی نیست.
- هر متن یک تجربهٔ جزئی، عینی، واقع‌نما و یک هستهٔ انگیزشی داشته باشد.
- متن منبع رضایت/کشش را بیان کند، نه صرفاً وظیفه، مهارت یا کلیشهٔ شغلی.
- با یک تا سه متن نزدیک از نظر فعالیت/فعل، موضوع یا منبع رضایت تمایز واقعی داشته باشد.
- فردیت حفظ شود و ادعا نشود همهٔ افراد یک رشته انگیزهٔ یکسان دارند.
- دست‌کم دو بازبین مستقل باید تناسب فعالیت واقعی حوزه و کیفیت/تمایز انگیزشی را بررسی و نام، تاریخ، دامنه و نظر خود را ثبت کنند.
- تغییر متن، کد و نسخهٔ متن باید در change record ثبت شود؛ متن تأییدنشده مبنای وزن‌دهی قطعی نیست.

## 4. معماری چهار دامنهٔ مستقل داده/اثر

چهار دامنه باید در رجیستری و گزارش‌ها مستقل باشند. پیاده‌سازی می‌تواند بعداً یک ماژول/رجیستری مشترک با چهار projection نسخه‌دار باشد؛ الزام، استقلال status و پوشش است، نه چهار فایل کد جدا.

| دامنه | معنای حاکمیتی | فیلدهای کاندیدا | الزام تغییر |
|---|---|---|---|
| A — Scientific / Scoring | ورودی‌های اثرگذار بر امتیاز عددی، eligibility، M/S/V و فاصلهٔ پروفایل | وزن‌های S/V، motive_driven، کدهای مؤثر M، مخرج M شاخه، وزن‌ها و mapping سؤال/گزینهٔ مؤثر بر scoring | scientific FAIL مستقل و بازبینی evidence/وزن؛ عضویت یا presentation PASS آن را جبران نمی‌کند. |
| B — Membership / Guidance | اتصال رشته به شاخه و هدایت تحصیلی/گروه سنجش | major_id → high_school_branch، exam_group و هر فیلدی که call-site واقعی نقش هدایت آن را ثابت کند | طبق §5 mismatch مستقل، blocking است؛ استثنا فقط با Decision Record مجاز است. |
| C — Evidence Content | متن شاهدی که micro-motive و وزن بر آن استوار است | micro_motives[].code → description_fa و provenance/نسخه/وضعیت تصویب متن | تغییر description حتی با وزن ثابت باید content/evidence review را فعال و وزن‌های متکی به آن را برای بازبینی علامت‌گذاری کند؛ این تغییر نباید به‌عنوان تغییر عدد وزن گزارش شود. |
| D — Interpretation / Presentation | معنای تفسیری و نمایش نتایج/پرسش‌ها | پرسش‌ها/گزینه‌های ارزشی، value_poles، trait_map، نام و متون نمایشی رشته/شاخه پس از اثبات call-site | تغییر باید در گزارش مستقل و بازبینی معنایی/UI ثبت شود؛ این دامنه محل پنهان‌کردن تغییر علمی یا membership نیست. |

### 4.1 فیلدهای مبهم

فیلدهای `group`، `cluster`، `subgroup`، `name`، `archetype`، `fulfillment_source`، `prestige_level`، `handcrafted`، `weights_version`، `value_poles` و `trait_map` تا تکمیل ماتریس زیر در هیچ projection نهایی بدون استدلال قرار نمی‌گیرند:

`field → consumer/call-site → owner → domain → mutation test → approval rule`

شناسهٔ پایدار رشته/شاخه باید حفظ شود تا اتصال هویتی وزن و membership مخدوش نشود.

### 4.2 وضعیت کد fingerprint فعلی

در deploy، `reference_fingerprints.py` موجود است و projectionهای علمی و membership را محاسبه می‌کند. بررسی نسخهٔ موجود نشان داده:
- scoring projection برای رشته‌ها id، motive_driven، weights_version، micro_motive_codes، strategy_weights و value_weights را می‌گیرد.
- scoring projection برای شاخه‌ها id/name، codes، m_score_denom_limit، S/V و weights_version را می‌گیرد.
- micro-motive در projection علمی فعلی فقط مجموعهٔ codeها را وارد می‌کند؛ description_fa وارد hash نمی‌شود.
- questions projection فعلی strategy questions را می‌گیرد؛ پوشش همهٔ پرسش‌های ارزشی/متن‌های تفسیری باید جداگانه تعیین شود.
- membership projection شامل id/name/high_school_branch/group/cluster/subgroup/exam_group رشته و id/name/group شاخه است؛ دامنهٔ هر فیلد هنوز باید با call-site کامل تطبیق داده شود.

در نتیجه، این ماژول فعلی معادل پیاده‌سازی کامل چهار دامنه نیست. قبل از افزودن projectionهای محتوایی/نمایشی، field map و mutation tests کامل لازم است.

## 5. سیاست مصوب membership — Fail-closed

تصمیم صریح ناظر:
- هر membership mismatch، حتی اگر scientific fingerprint بدون تغییر و PASS باشد، باید یک FAIL مستقل و مسدودکننده ایجاد کند.
- PASS علمی، FAIL عضویت را جبران نمی‌کند و PASS عضویت نیز تغییر علمی را نمی‌پوشاند.
- تنها استثنا، تغییر membership دارای Decision Record نسخه‌دار با شناسه و مقدار قبل/بعد، منبع و توجیه آموزشی/داده‌ای، اثر مصرف‌کنندگان، شواهد بازبینی و تأیید صریح ناظر است.
- استثنا باید در PR جداگانه با baseline کنترل‌شده انجام شود؛ update expected برای سبزکردن CI، تصمیم محسوب نمی‌شود.
- تست mutation باید اثبات کند تغییر تک‌فیلدی membership فقط status عضویت را تغییر می‌دهد و تغییر صرفاً علمی فقط status علمی را.

**وضعیت اجرا:** این سیاست در این رجیستری ثبت شده است؛ هنوز به workflow یا gate اجرایی منتقل نشده است.

## 6. مالکیت main/deploy و ورودی‌های مشترک

تفکیک پیشنهادی فعلی:
- ورودی‌های مشترک مصرف‌شده توسط UI و موتور، مانند `docs/data/questions_v2.json`، `docs/data/trait_map_v3.json` و `value_poles_v2.json`، قرارداد هم‌معنایی/تطبیق byte با نسخهٔ shared باید داشته باشند.
- داده‌های علمی runtime-owned مانند `majors_database_v2.json`، `micro_motives.json` و `school_branches_v2.json` نباید با main به‌صورت خودکار sync شوند؛ با fingerprint و evidence مستقل حفاظت شوند.
- هر دو مسیر `micro_motives.json` ریشه و `docs/data/micro_motives.json` باید پوشش داده شوند یا هم‌ارزی دقیق آن‌ها در همان commit assert شود؛ موتور مسیر root را به‌طور پیش‌فرض می‌خواند.
- نقش main/deploy و owner هر منبع باید در رجیستری باشد. تغییر main هیچ مجوزی برای کپی به deploy ایجاد نمی‌کند.

PR #321 در وضعیت فعلی مبنای اجرای این قرارداد نیست: base آن قدیمی است، مسیر root micro_motives را فهرست نکرده و workflow مربوط به Hybrid Migration Audit را هم تغییر می‌دهد. بازطراحی آن باید اتمیک، روی base جاری و با scope مصوب جداگانه باشد. هیچ تغییری در Hybrid/cutover با این سند مجاز نیست.

## 7. رجیستری validatorها

هر ابزار ماشینی باید با نام/مسیر، commit و blob دقیق، ورودی و SHA داده، دامنه، معنای exit code، محدودیت، workflow مصرف‌کننده و مدرک اجرای همان commit ثبت شود.

| ابزار | مرجع نسخه | نقش | قرارداد خروجی و محدودیت |
|---|---|---|---|
| `validate_integrity.py` | PR #307 در main؛ blob `eec5ea7799640bf4fff85ab76559dbfbb8d08bd9` | ساختار/ارجاع رشته‌های فعال و شاخه‌ها، S 25×5، V 30 کلید، refs، questions/trait map و signature collision | exit 1 در خطا و exit 0 در موفقیت. نسخهٔ ثبت‌شده برای S کنترل صریح finite ندارد؛ تا رفع این محدودیت و تست منفی، به‌تنهایی validator نهایی NaN/Infinity محسوب نمی‌شود. |
| `global_separation_test.py` | PR #307 در main؛ blob `485e2f4a7f90a223a433919e12f94c720a89f857` | گزارش Pearson راهبردی/ارزشی/ترکیبی، جفت‌های نزدیک و برخورد signature | آستانه‌های Pearson صرفاً تشخیصی‌اند؛ ابزار گزارش‌محور است و به‌تنهایی gate رد/قبولی نیست. خطاهای ورودی/محاسبه exit غیرصفر دارند. |
| تست finite فعلی deploy | `test_reference_finite_startup.py` در snapshot deploy | کنترل finite بودن دادهٔ مرجع در مسیر startup | باید جداگانه با ورودی/commit خود ثبت و اجرا شود؛ PASS آن دامنهٔ سایر تست‌های validator را پوشش نمی‌دهد. |

الزام پیش از هر PR داده‌ای:
1. validator ساختاری روی همان snapshot داده اجرا شود؛ هر exit غیرصفر یا خطای ساختاری مانع پذیرش است.
2. پس از رفع محدودیت finite در نسخهٔ validator، نسخهٔ pin‌شدهٔ آن با blob دقیق و گزارش اجرا ثبت شود؛ تا آن زمان تست finite موجود نباید حذف یا تضعیف شود.
3. برای تغییر `majors_database_v2.json`، global separation report نیز روی همان snapshot ثبت شود؛ Pearson thresholdها به‌تنهایی blocking نیستند، برخورد signature باید از validator ساختاری و داوری بررسی شود.
4. evidence packet، provenance و دو امضای مستقل متن نیز لازم‌اند؛ PASS ماشینی تأیید علمی نیست.
5. اجرا روی main و داده از deploy بدون ثبت هر دو SHA قابل قبول نیست.
6. در حال حاضر این دو اسکریپت در main هستند و در snapshot deploy حضور ندارند؛ اجرای آن‌ها در CI deploy را نباید ادعا کرد. انتقال/backport یا اتصال workflow نیازمند PR و مجوز جداگانه است.

## 8. کنترل نسخه، baseline و گزارش اجرای اجباری

- هر گزارش باید commit داده، blobهای فایل‌های ورودی، commit/blob validator، command line، خروجی کامل، exit code و workflow run لینک‌شده را ثبت کند.
- baselineهای فعلی fingerprint در `reference_fingerprints.py` برای rangeهای انتهایی 194، 204 و 215 تعریف شده‌اند؛ این دامنه مساوی پوشش کامل 230 رشته نیست.
- `FINGERPRINT_BASE_COMMIT=02f40f16e044219141a1d354d9d1aa30df416d87` با snapshot مبنای ممیزی `a743ab8ddd335c49e579299f062778bd4f8e6e85` متفاوت است. این اختلاف قبل از هر expected refresh باید forensic و مستند شود.
- هیچ expected، projection version یا baseline برای سبزکردن CI تغییر نمی‌کند؛ هر تغییر فقط با forensic، decision record و PR اتمیک مجاز است.
- موفقیت Liara Runtime Lock، به‌تنهایی اعتبار علمی یا مجازبودن تغییر baseline را ثابت نمی‌کند.
